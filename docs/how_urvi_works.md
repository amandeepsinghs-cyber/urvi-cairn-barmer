# How Urvi works: architecture explained

_Generated by `frontend/scripts/build_architecture.py` from `frontend/scripts/architecture_explain.py`; the same text appears in the app (Architecture tab → **Explain**). Do not edit by hand._

## How Urvi works today (V 1.0 demo)

Urvi is one AI agent with a set of engineering tools. The AI model understands the question and decides which tools to call; the tools do the calculations on well data; the model then explains the result in a few sentences. The model never invents numbers.

### Three ways a request is handled

| You say or type | What handles it | AI involved? |
|---|---|---|
| A plain screen command, e.g. "full screen", "GGS three dikhao", "show me the architecture" | A rule-based parser in the browser changes the screen directly | No |
| A typed question, e.g. "Which field is underperforming?" | The ADK agent: one agent on Gemini 3.8 Flash with 34 tools | Yes |
| A spoken question (Live voice) | Gemini 3.8 Live through our Live proxy, with 13 voice tools (ADK is not used for voice) | Yes |

### A typed question, step by step

- **① You ask:** You type in the Urvi panel. The browser checks whether it is a plain screen command; if not, it sends the question to the Urvi API, with the screen context (field, well, language).
- **② Urvi API:** A Python web service (FastAPI) on Cloud Run receives the request at /api/chat. It also serves the web app itself.
- **③ ADK agent:** The API hands the question to the agent, built with Google's Agent Development Kit (ADK). There is one agent, named "wellpulse". Its instructions describe the 5-level drill-down (field → health → priority list → well → next best action) and which tool answers what.
- **④ Gemini 3.8 Flash:** The agent sends the question and the tool list to Gemini. Gemini replies with the tool(s) to call, e.g. compare_fields. After the tools run, it gets their results back and writes a short answer (2–4 sentences).
- **⑤ Tools:** Each tool is ordinary Python code: decline attribution, well health, ranking, next best action, document search, and so on. Several tools can be called in one turn.
- **⑥ Well data:** The tools read the well tables (production, pressures, completion, job history) through the data access layer. In the demo these are synthetic parquet files packed into the app.
- **⑦ Answer + screen:** The answer goes back to the browser together with screen actions, so the matching view opens (chart, completion diagram, recommendation). A guard checks that every number in the answer appears in a tool result; any other number is masked.

### A spoken question, step by step

- **Ⓐ Audio in:** The browser streams your microphone (16 kHz) over a WebSocket to the Gemini Live proxy on our server, and plays Urvi's spoken reply (24 kHz). You can interrupt at any time.
- **Ⓑ Gemini 3.8 Live:** The proxy connects to Gemini Live, a speech-to-speech model. It hears the question, decides which voice tool to call, and speaks the answer (voice: Aoede). English by default; Hindi or Hinglish if you switch.
- **Ⓒ Same tools:** Voice tools run on our server and call the same analytics code as chat. There are fewer of them (13) because a voice model works best with a short list; some bundle several chat tools, e.g. well_profile also returns offset decline, anomalies and wax / sand.

### Is it a multi-agent system?

No. Urvi is a single agent with many tools: one ADK agent for chat and one Gemini Live session for voice. There are no sub-agents and no agent-to-agent hand-offs.

The design allowed splitting into specialist sub-agents if the agent picked the wrong tool too often (below 90%). The evaluation scored 46 of 46 (100%), so one agent is enough.

How to say it: "One Urvi agent with 34 engineering tools for chat, and the same tools through Gemini Live for voice. Every number comes from deterministic tools, never from the model."

### Where the recommendations come from

The next-best-action tool combines physics checks (water diagnostics, pump signatures, offset wells, pressure surveys), a trained intervention classifier, historical success rates and look-alike wells, and returns a ranked top 3 with probability of success, expected gain, rig-days and the SOP.

Full explanation, with a worked example: docs/ml_recommendation_engine.md.

### Data, build and identity (the grey lines)

Data: a seeded generator creates 412 synthetic wells (Geleki, Lakwa, Lakhmani, 60 months). The app reads parquet copies packed into the container; the same data also sits in a BigQuery medallion lakehouse (Bronze → Silver → Gold) in Mumbai (asia-south1).

Build: Cloud Build builds the container image and stores it in Artifact Registry; Cloud Run runs it as one instance (sessions are kept in memory).

Identity: Cloud Run runs as a dedicated service account and reaches Gemini and BigQuery without API keys.

### Why the demo runs in the US region

Gemini Live is not yet offered in India regions, so the demo runs in us-central1. It uses only synthetic data. The production design runs in India regions: see the Target view.

### Words used

| Term | Meaning |
|---|---|
| Cloud Run | Google's service that runs our container and scales it |
| ADK | Agent Development Kit: Google's framework for building agents that call tools |
| Gemini 3.8 Flash | The text model behind the chat agent |
| Gemini 3.8 Live | The speech-to-speech model behind voice |

## How Urvi would work in production for ONGC

Same agent, same tools, real data. ONGC's systems feed the ONGC Enterprise Data Platform (EDP); Urvi reads a governed "Well Health" data product from the EDP; Urvi and Gemini run in Google Cloud India regions; nothing leaves India. AI runs in the cloud, as the EDP RFP places it.

### A question, step by step

- **① Sign in:** Users reach Urvi through Identity-Aware Proxy with their ONGC login (single sign-on). Typed and voice traffic both enter here.
- **② Urvi API + web app:** The same service as the demo, on Cloud Run in Mumbai, scaling with load.
- **③ ADK agent:** The same single agent and tools as the demo; role-based access is enforced.
- **④ Gemini (India):** Gemini on Vertex AI India regional endpoints. ONGC data is not used to train models.
- **⑤ Tools:** The same engineering tools, plus nightly scores from the trained recommendation models.
- **⑥ EDP data adapter:** A new adapter in Urvi's data access layer. It replaces the demo's parquet files.
- **⑦ EDP consumption API:** The adapter reads the Well Health data product through the EDP's API (the RFP allows no direct database queries).

### Voice

- **Ⓑ Gemini Live (India):** The Live proxy connects to Gemini Live on an India endpoint at go-live.
- **Ⓒ Same tools:** Voice tools call the same analytics code as chat.

### Where the data comes from

- **D1 ONGC systems → EDP on-prem:** Production / DPR, SCADA + OSI PI, WIS / EDS, SAP, LIMS and DISHA are ingested by the EDP's ingestion layer (UDEL) in ONGC's data centres. Raw Category A data (e.g. raw SCADA) stays there.
- **D2 Interconnect:** Data that ONGC places in the cloud zone travels over a private link (Cloud Interconnect), encrypted.
- **D3 Bronze → Silver → Gold:** The EDP cloud zone cleans and curates it into the Well Health data product.
- **D4 Consumption API:** The product is published through the EDP API, which Urvi reads (step 7).

### Two other routes (dashed)

Route B: the data stays on-prem and Urvi, still in the cloud, reads only the rows it needs from the on-prem EDP API over the private link.

Route P (pilot): before the EDP is live, ONGC exports 10–20 mature Assam wells (names masked) to a landing bucket in Mumbai, so Urvi can be proven on real data in weeks.

### How it stays in India and secure

Mumbai (asia-south1) is the primary region and Delhi (asia-south2) the disaster-recovery region; both are MeitY-empanelled and accepted as India-resident by the RFP (§3.2.6).

ONGC holds the encryption keys (Cloud KMS, CMEK / EKM); a VPC Service Controls perimeter prevents data copies leaving the project; Access Approval means Google support access needs ONGC's approval; logs stay in India for at least 180 days.

### What changes from the demo

| Area | Demo | Production |
|---|---|---|
| Region | us-central1 (Gemini Live) | asia-south1 / asia-south2 |
| Data | Synthetic, packed into the app | ONGC EDP Well Health product via API |
| Access | Public demo URL | IAP + ONGC single sign-on, role-based access |
| Scale | One instance, in-memory sessions | Autoscaling, Memorystore session store |
| Recommendations | Classifier + rates + look-alikes | Models trained on ONGC history (Vertex AI) |
| Documents | Keyword search | Vertex AI Search |
