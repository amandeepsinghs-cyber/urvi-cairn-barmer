# How Urvi works: architecture explained

_Generated by `frontend/scripts/build_architecture.py` from `frontend/scripts/architecture_explain.py`; the same text appears in the app (Architecture tab → **Explain**). Do not edit by hand._

## How Urvi works today (V 1.0 demo)

Single-Agent, Multi-Tool Hybrid Architecture — natural spoken & typed language in (Gemini ADK / Live) → deterministic engineering physics, ML models & numeric-grounding guards underneath (best of both worlds with minimal hallucination). Urvi is one AI agent with a set of engineering tools. The AI model understands the question and decides which tools to call; the tools do the calculations on well data; the model then explains the result in a few sentences. The model never invents numbers.

### Three ways a request is handled

| You say or type | What handles it | AI involved? |
|---|---|---|
| A plain screen command, e.g. "full screen", "Mangala dikhao", "show me the architecture" | A rule-based parser in the browser changes the screen directly | No |
| A typed question, e.g. "Which field is underperforming?" | The ADK agent: one agent on Gemini 3.8 Flash with 34 tools | Yes |
| A spoken question (Live voice) | Gemini 3.8 Live through our Live proxy, with 13 voice tools (ADK is not used for voice) | Yes |

### A typed question, step by step

- **① You ask:** You type in the Urvi panel. The browser checks whether it is a plain screen command; if not, it sends the question to the Urvi API, with the screen context (field, well, language).
- **② Urvi API:** A Python web service (FastAPI) on Cloud Run (urvi-cairn-app) receives the request at /api/chat. It also serves the web app itself.
- **③ ADK agent:** The API hands the question to the agent, built with Google's Agent Development Kit (ADK). There is one agent, named "urvi_agent". Its instructions describe the 5-level drill-down (field → health → priority list → well → next best action) and which tool answers what.
- **④ Gemini 3.8 Flash:** The agent sends the question and the tool list to Gemini. Gemini replies with the tool(s) to call, e.g. compare_fields. After the tools run, it gets their results back and writes a short answer (2–4 sentences).
- **⑤ Tools:** Each tool is ordinary Python code: decline attribution, well health, ranking, next best action, document search, and so on. Several tools can be called in one turn.
- **⑥ Well data:** The tools read the well tables (production, pressures, completion, job history) through the data access layer. In the demo these are synthetic parquet files packed into the app.
- **⑦ Answer + screen:** The answer goes back to the browser together with screen actions, so the matching view opens (chart, completion diagram, recommendation). A guard checks that every number in the answer appears in a tool result; any other number is masked.

### A spoken question, step by step

- **Ⓐ Audio in:** The browser streams your microphone (16 kHz) over a WebSocket to the Gemini Live proxy on our server, and plays Urvi's spoken reply (24 kHz). You can interrupt at any time.
- **Ⓑ Gemini 3.8 Live:** The proxy connects to Gemini Live, a speech-to-speech model. It hears the question, decides which voice tool to call, and speaks the answer (voice: Aoede). English by default; Hindi or Hinglish if you switch.
- **Ⓒ Same tools:** Voice tools run on our server and call the same analytics code as chat. There are fewer of them (13) because a voice model works best with a short list; some bundle several chat tools, e.g. well_profile also returns offset decline, anomalies and wax / sand.

### Is it a multi-agent system?

No. Urvi is a single agent with many tools: one ADK agent for chat and one Gemini Live session for voice. There are no sub-agents and no agent-to-agent hand-offs.

The design allowed splitting into specialist sub-agents if the agent picked the wrong tool too often (below 90%). The evaluation scored 46 of 46 (100%), so one agent is enough.

How to say it: "One Urvi agent with 34 engineering tools for chat, and the same tools through Gemini Live for voice. Every number comes from deterministic tools, never from the model."

### Where the recommendations come from

The next-best-action tool combines physics checks (water/polymer breakthrough diagnostics, pump signatures, offset wells, pressure surveys), a trained intervention classifier, historical success rates and look-alike wells, and returns a ranked top 3 with probability of success, expected gain, rig-days and the SOP.

Full explanation, with a worked example: docs/ml_recommendation_engine.md.

### Data, build and identity (the grey lines)

Data: a seeded generator creates 460 synthetic wells across Barmer Basin (Mangala, Bhagyam, Aishwariya, Raageshwari; 60 months). The app reads parquet copies packed into the container; the same data sits in gs://urvi-cairn-barmer-ai-agent-datalake and a BigQuery medallion lakehouse (urvi_cairn_bronze → urvi_cairn_silver → urvi_cairn_gold) in Mumbai (asia-south1).

Build: Cloud Build builds the container image and stores it in Artifact Registry; Cloud Run runs urvi-cairn-app as one instance (sessions are kept in memory).

Identity: Cloud Run runs as a dedicated service account and reaches Gemini and BigQuery without API keys.

### Why the demo runs in the US region

Gemini Live is not yet offered in India regions, so the demo runs in us-central1. It uses only synthetic data. The production design runs in India regions: see the Target view.

## How Urvi works in production for Cairn Oil & Gas (Vedanta)

Single-Agent, Multi-Tool Hybrid Architecture — natural spoken & typed language in (Gemini ADK / Live) → deterministic engineering physics, ML models & numeric-grounding guards underneath (best of both worlds with minimal hallucination). Same agent, same tools, governed production data. Cairn / Vedanta upstream systems feed the Vedanta Enterprise Data Lakehouse in Google Cloud Mumbai (asia-south1); Urvi reads governed well health and intervention tables; Urvi and Gemini run in India regions with VPC Service Controls and CMEK.

### A question, step by step

- **① Sign in:** Users reach Urvi through Identity-Aware Proxy with Vedanta single sign-on and role-based access control (COO / CIO, Asset Manager, Production Engineer). Typed and voice traffic both enter here.
- **② Urvi API + web app:** The same service as the demo, on Cloud Run in Mumbai (asia-south1), scaling with load.
- **③ ADK agent:** The same single agent and tools as the demo; persona and field access are enforced.
- **④ Gemini (India):** Gemini on Vertex AI India regional endpoints. Cairn / Vedanta data is never used to train models.
- **⑤ Tools:** The same engineering tools, plus nightly scores from the trained recommendation models.
- **⑥ Lakehouse data adapter:** A governed data-access adapter replacing the demo's baked parquet files.
- **⑦ Lakehouse Consumption API:** The adapter reads the curated Well Health & Opportunity tables through a scoped consumption API (or governed BigQuery Silver/Gold views).

### Voice

- **Ⓑ Gemini Live (India):** The Live proxy connects to Gemini Live on an India regional endpoint at go-live.
- **Ⓒ Same tools:** Voice tools call the same analytics code as chat.

### Where the data comes from

- **D1 Cairn / Vedanta upstream sources [verify]:** AVEVA / OSIsoft PI Historian & Pad SCADA (MPT Nagana, RGT, Jet-Pump/ESP telemetry) [verify], SAP S/4HANA PM/MM (work orders, rig schedule, MRO spares) [verify], and WellView / Subsurface Well-File DMS (DWRs, CBLs, completion tallies) [verify] feed the on-site collector.
- **D2 Private Interconnect:** Curated telemetry aggregates, work orders, and documents transfer to Mumbai over a private encrypted link (Cloud Interconnect).
- **D3 Vedanta Enterprise Data Lakehouse:** Ingested into Bronze → Silver → Gold in asia-south1 (Mumbai) using Dataflow / BigQuery / Dataform.
- **D4 Consumption API:** Governed Well Health and dossier facts are published via Apigee / Consumption API, which Urvi reads (step 7).

### Two other routes (dashed)

Route B: raw high-frequency historian data remains on-site and Urvi, in asia-south1, queries only aggregated well metrics over the private Interconnect API.

Route P (pilot): before full enterprise connectors go live, Barmer Basin exports a masked pilot slice of mature Mangala / Bhagyam / Aishwariya / Raageshwari wells to a CMEK-encrypted Mumbai GCS bucket.

### Security, residency and governance in India

Mumbai (asia-south1) serves as primary region and Delhi (asia-south2) as disaster-recovery region; all data, models, and logs remain resident in India.

Vedanta holds encryption keys (Cloud KMS, CMEK / EKM); a VPC Service Controls perimeter prevents data exfiltration; Access Approval enforces customer sign-off for support access; audit logs are retained in India and forwarded to Vedanta security monitoring.
